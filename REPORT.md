| **Идентификатор версии** | Git-коммит + хэш внутри `data.dvc` (например, коммит `ed0c0f7` и хэш `bf5656de...`). | Dataset ID (уникальный UUID, например `c3bd61e2...`) и Version (например, `1.0.0`). |
| **Расположение метаданных** | В Git-репозитории, в текстовых файлах `*.dvc`. | На сервере ClearML. |

| **Способ создания дочерней версии** | Создание новой Git-ветки (`git switch -c`), генерация файлов и `dvc add data`. | Вызов `Dataset.create(..., parent_datasets=[BASE_ID])` и добавление новых файлов. |
| **Способ переключения версии** | `git switch <branch>` + обязательное выполнение `dvc checkout` для обновления файлов в workspace. | Получение по `Dataset.get(dataset_id=...)` и скачивание в локальную папку. |
| **Способ восстановления на чистой машине** | `git clone` + `dvc pull` (данные подтягиваются из remote). | `Dataset.get(dataset_id=...).get_mutable_local_copy()`. |
| **Поведение при ветвлении** | Естественное ветвление через Git branches (например, `feature/wine` и `feature/iris-features`). | Создание нескольких дочерних версий от одного родителя (DAG-граф в lineage). |
| **Поведение при слиянии** | Выполняется через `git merge` с настроенным DVC merge driver. В работе слияние прошло автоматически без конфликтов. | Слияние не предусмотрено в явном виде; требуется создание новой версии с указанием нескольких родителей. |
| **Связь версии данных с Git** | Жесткая. Версия данных привязана к конкретному коммиту и ветке. | Отсутствует. Датасеты существуют независимо от Git-истории кода. |
| **Доступность через UI** | Зависит от сторонних сервисов (GitHub/GitLab), сами данные в UI не видны. | Встроенный Web UI ClearML (просмотр lineage, состава файлов и логов). |


Ответы на вопросы

Какой объект однозначно определяет версию данных в DVC?
Версию определяет конкретный Git-коммит (фиксирующий состояние data.dvc) и MD5-хэш самого файла или директории, указанный внутри data.dvc. Только вместе они дают точное указание на версию.

Почему одного Git-коммита недостаточно без DVC remote?
Git-коммит содержит только метаданные (data.dvc), но не сами данные. Если локальный кэш DVC утерян (например, при клонировании на другую машину), Git не сможет восстановить CSV. DVC remote выступает единым хранилищем, откуда dvc pull скачивает содержимое.

Чем Dataset version отличается от Dataset ID в ClearML?
Dataset version — это человекочитаемая строка (например, "1.0.0"), которую можно задать вручную. Dataset ID — это уникальный UUID, генерируемый системой. Version может быть продублирована, а ID неизменен и гарантирует доступ к конкретному объекту.

Почему finalize() нельзя считать созданием следующей версии?
finalize() переводит текущую версию в статус Completed и делает её неизменяемой (read-only). Он не создаёт новый объект, не инкрементирует версию и не копирует данные. Для новой версии нужно вызвать Dataset.create() с новым номером.

Как доказать, что ClearML version 2.0.0 создана от базы, а не от 1.1.0?
Это доказывается через граф зависимостей (lineage). В коде при создании 2.0.0 явно указано parent_datasets=[BASE_ID]. Dependency Graph показывает прямую стрелку от 1.0.0 к 2.0.0. Кроме того, в списке файлов версии 2.0.0 отсутствует wine.csv, который был бы унаследован от 1.1.0.

Что произойдёт, если после git switch не выполнить DVC checkout?
Файл data.dvc обновится до состояния новой ветки, но сами данные в рабочей директории (папка data/) останутся от предыдущей ветки. Это приведёт к рассинхронизации: dvc status покажет изменения, а данные не будут соответствовать выбранному Git-коммиту.

В каком сценарии этой работы удобнее DVC, а в каком ClearML Dataset?

DVC удобнее для разработчиков: он интегрирован с Git и идеален для ветвления данных параллельно с кодом (как в ветках с Wine и Iris features) и слияния изменений.

ClearML Dataset удобнее для командной работы: он даёт прозрачный lineage (граф происхождения), Web UI для просмотра и связывает данные с экспериментами без клонирования Git-репозитория.
